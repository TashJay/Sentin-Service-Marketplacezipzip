# SENTIN — BUILD A MONETIZABLE CHATGPT APP

## CRITICAL PRODUCT DIRECTION

You are building **Sentin**, a global AI-powered real-world services marketplace whose **primary product is a ChatGPT App**.

Do NOT treat Sentin as a normal website with a ChatGPT integration added later.

The priority is:

**CHATGPT USER → SENTIN CHATGPT APP → SENTIN SERVICE MARKETPLACE → REAL-WORLD SERVICE PROVIDER → TRANSACTION**

The standalone Sentin website/backend exists to power the ChatGPT App, manage providers, jobs, quotes, bookings, payments, trust, and administration.

The first objective is to prove the **ChatGPT-to-real-world-service transaction loop**.

Do not over-engineer the first release into a massive Uber-scale marketplace.

Build a production-quality V1 that can actually be connected to ChatGPT, tested through ChatGPT conversations, and eventually submitted as a ChatGPT App.

OpenAI's current ecosystem uses the **Apps SDK/MCP architecture**, so implement against the current official Apps SDK/MCP requirements rather than an obsolete legacy-plugin architecture. Verify the current official documentation during implementation instead of relying on assumptions.

---

# 1. PRODUCT VISION

Sentin solves a simple problem:

> **People know what problem they have, but often don't know who to call, what the service should cost, or how to arrange it.**

Instead of searching Google, browsing directories, calling several businesses, comparing prices, and coordinating appointments, the user simply tells ChatGPT what they need.

Example:

> "My washing machine is leaking."

Sentin should understand the problem, ask only the necessary questions, determine the user's location, find appropriate service providers, obtain quotes where necessary, present the options clearly, and allow the user to proceed toward booking.

Another example:

> "I need a photographer for a wedding in Manchester next month."

Sentin should understand:

* service type
* location
* date
* approximate duration
* requirements
* budget if relevant

Then search the marketplace and return appropriate providers.

Another:

> "I need someone to repair the AC in my office."

Sentin should determine whether this is:

* residential
* commercial
* emergency
* inspection required
* quote required

and proceed accordingly.

# 6. READ VS WRITE OPERATIONS

Separate read operations from operations that change state.

Examples:

### Read

```text
search providers
view provider
view job
view quotes
view booking
view messages
```

### Write

```text
create job
request quotes
accept quote
create booking
cancel booking
send message
create review
create dispute
```

All write operations must have:

* authentication where required
* authorization
* validation
* idempotency where appropriate
* audit logging
* clear success/failure responses

Never tell the user that an action happened unless the backend actually confirmed it.

For example, NEVER say:

> "Your booking is confirmed."

unless the booking transaction actually succeeded.

# 9. THE SENTIN CONVERSATIONAL ENGINE

Sentin needs structured job understanding.

When a user says:

> "My fridge is making a weird noise."

The system should internally produce something similar to:

```json
{
  "service_category": "appliance_repair",
  "service_type": "refrigerator_repair",
  "problem": "unusual_noise",
  "location": null,
  "urgency": "unknown",
  "property_type": "unknown",
  "known": [],
  "inferred": [],
  "unknown": [
    "location",
    "noise_type",
    "whether_unit_is_still_cooling"
  ]
}
```

The AI should then ask the minimum useful questions.

Do not interrogate the user with ten questions.

Ask only questions that materially affect:

* provider matching
* price
* urgency
* safety
* availability
* service requirements

---

# 10. AI MUST NOT INVENT FACTS

This is extremely important.

The AI must distinguish:

### Known

Information provided by the user or verified by the system.

### Inferred

Reasonable interpretation that may require confirmation.

### Unknown

Information that has not been established.

Never invent:

* providers
* prices
* availability
* reviews
* credentials
* licenses
* bookings
* quotes
* service completion
* payment status

If no providers exist:

> "I couldn't find matching providers in that area."

Do not manufacture alternatives.

---

# 11. SERVICE ESTIMATES VS PROVIDER QUOTES

These must be separate concepts.

### AI estimate

Example:

> "Similar washing-machine repair jobs commonly fall around £60–£120, but this is only an estimate."

### Provider quote

Example:

> "Alex Appliance Repair quoted £85."

Never present an AI estimate as an actual provider price.

Never present a provider quote as an AI estimate.

# 30. ERROR HANDLING

Design explicitly for failures.

Examples:

### No providers

> "I couldn't find available providers for that service in your area."

### Provider doesn't respond

> "Two providers haven't responded yet. Would you like me to try additional providers?"

### Quote expired

> "That quote has expired. I can request a fresh quote."

### Booking conflict

> "That time is no longer available. Here are the next available slots."

### Payment failure

> "The payment wasn't completed. No booking was confirmed."

### Provider cancels

Automatically return the job to a recoverable state and offer alternatives.

Never hide backend failures behind confident AI language.
